Project: Offline-First Smart Gate Management System
1. Project Overview

We are developing a complete offline-first, full-stack Smart Gate Management System designed to manage and monitor the entry and exit of employees, staff members, and other authorized individuals within an organization's premises.

The system integrates hardware-based access control with a centralized web application running on a local Raspberry Pi server.

This is a completely on-premises, LAN-based application. It must operate independently without requiring an internet connection or external cloud services.

The primary objective is to automate gate operations using RFID cards and fingerprint authentication, maintain accurate entry/exit records, and provide authorized security guards with a web-based interface to control the gate manually.

2. System Architecture

The project consists of three major components:

ESP32-based Smart Gate Controller.
Raspberry Pi-based Local Server.
Next.js Full-Stack Web Application.

All three components communicate over the local network.

A. ESP32-Based Smart Gate Controller

The ESP32 acts as the physical gate control unit. It is responsible for hardware-level authentication and controlling the gate mechanism.

Hardware components:

ESP32 microcontroller.
Fingerprint sensor.
RFID card reader.
Stepper motor for gate operation.

Expected functionality:

When an individual approaches the gate, they can authenticate using either:
Registered fingerprint.
Registered RFID card.
The ESP32 validates the authentication request against the locally available authorized credentials or an appropriate local server authentication mechanism.
If authentication is successful:
The ESP32 activates the stepper motor.
The gate opens automatically.
The system records the access event.
The event is synchronized with the central application/database.
If authentication fails:
The gate remains closed.
The failed authentication attempt is recorded where connectivity permits.
Unauthorized access is prevented.
The ESP32 must also support remote gate control through the web application.
The hardware communication mechanism must be reliable, with proper authentication, error handling, and connection-status monitoring.
B. Raspberry Pi – Local Server

The Raspberry Pi acts as the centralized local server for the complete gate management ecosystem.

Environment:

Raspberry Pi board.
Ubuntu Server (CLI version).
Next.js full-stack application.
Local database.
LAN network connectivity.

Responsibilities:

Host and run the complete web application locally.
Provide access to the application through the organization's LAN.
Act as the central communication point between the ESP32 gate controllers and the web application.
Manage employee information, authentication credentials, access permissions, and gate activity records.
Receive entry/exit events from ESP32 devices.
Store all access records in the local database.
Provide gate-control commands to ESP32 devices when authorized users request manual operation.
Maintain application availability without depending on external internet connectivity.

The Raspberry Pi should function as an independent on-premises server.

C. Next.js Full-Stack Web Application

The Next.js application provides the administrative dashboard, security guard interface, employee management, access monitoring, and reporting functionality.

The application must communicate with ESP32 devices through the Raspberry Pi-hosted local backend.

Core functionalities:

1. Employee Management
Employee and staff records are already maintained in the database.
Each employee has a unique identification number.
Employee information includes relevant personal details, department, designation, RFID card mapping, and fingerprint registration status.
Only authorized employees should be allowed to access the premises.
2. Entry and Exit Management
Record every successful gate access event.
Maintain separate entry and exit records.
Store employee ID, employee name, gate ID, authentication method, event timestamp, and access direction.
Track how many individuals enter and leave the premises.
Provide real-time or near-real-time access activity monitoring.
Maintain a complete historical access log.
3. Automated Authentication
Support RFID-based authentication.
Support fingerprint-based authentication.
Validate access against registered employee records.
Automatically trigger gate opening after successful authentication.
Reject unauthorized access.
Ensure each successful access event is recorded accurately.
4. Manual Gate Control
Authorized security guards must be able to open the gate through the web application.
Manual gate control must be available through a secure HTTPS connection.
Only users with the appropriate RBAC permissions can perform gate operations.
Every manual gate operation must be recorded with the operator's identity, timestamp, gate ID, and operation type.
The system should provide feedback about gate command status.
5. Dashboard and Monitoring

The dashboard should provide:

Total registered employees.
Total entries for the current day.
Total exits for the current day.
Current estimated number of people inside the premises.
Recent access activities.
Gate status (open/closed/unknown).
ESP32 device connectivity status.
Failed authentication attempts.
Manual gate operation history.
6. Access Logs and Reports
View complete entry/exit history.
Filter records by employee, date, department, gate, and authentication method.
Generate daily, weekly, and monthly reports.
Export relevant reports when required.
Maintain reliable and traceable access records.
3. Existing RBAC Implementation

Important: The Role-Based Access Control (RBAC) system and login functionality have already been implemented.

Do not rebuild, replace, or unnecessarily modify the existing authentication and authorization architecture.

The application already has:

Employee login using assigned ID and password.
Role-based authentication.
Permission-based access to application interfaces.
Different dashboards and functionalities according to user roles.

All new functionalities must integrate with the existing RBAC implementation.

For example:

Administrators can manage employees, devices, gates, and system configurations.
Security guards can monitor access activities and manually operate authorized gates.
Other staff members should only access the functionalities permitted by their assigned roles.

Always inspect the existing RBAC implementation before introducing new permissions or modifying protected routes.

4. Overall System Workflow
Workflow 1: Automatic Entry/Exit Through RFID or Fingerprint
An employee approaches the gate.
The employee scans their registered RFID card or fingerprint.
The ESP32 processes the authentication request.
The system verifies whether the employee is authorized.
If authorized, the ESP32 activates the stepper motor.
The gate opens.
The access event is transmitted to the Raspberry Pi.
The backend saves the event in the database.
The dashboard updates the access activity.

If authentication fails, the gate must remain closed and the failure should be handled appropriately.

Workflow 2: Manual Gate Operation Through Web Application
A security guard logs in using their existing credentials.
The application verifies their identity and RBAC permissions.
The guard opens the gate-control interface.
The guard selects the appropriate gate.
The guard requests a manual gate-opening operation.
The backend validates the request and sends an authenticated command to the corresponding ESP32.
The ESP32 executes the command.
The application receives the command execution status.
The manual operation is recorded in the database.
Workflow 3: Centralized Access Monitoring
ESP32 devices generate access events.
Events are transmitted to the Raspberry Pi.
The backend validates and processes the events.
The database stores the access records.
The dashboard displays updated entry/exit statistics.
Administrators and authorized security personnel can monitor activity according to their permissions.
5. Important Technical Requirements

The following requirements must be considered throughout development:

Offline-first architecture: The application must function without internet connectivity.
LAN communication: ESP32 devices and the Raspberry Pi must communicate over the local network.
HTTPS security: Protect web application access and sensitive communication.
Device authentication: Only registered ESP32 devices should be allowed to communicate with the backend.
RBAC integration: All new application features must respect existing roles and permissions.
Data consistency: Avoid duplicate access events and incorrect entry/exit counts.
Reliability: Handle network disconnections, device restarts, and temporary communication failures.
Event synchronization: Ensure locally generated events are eventually synchronized when network connectivity is restored.
Auditability: Maintain a traceable history of automatic and manual gate operations.
Scalability: Support multiple gates and multiple ESP32 controllers.
Security: Never expose sensitive employee information, credentials, or biometric data unnecessarily.
6. Critical Business Logic

Pay special attention to the following:

A successful RFID or fingerprint authentication must result in an authorized gate operation.
Authentication and physical gate movement should be treated as separate events.
Do not assume that issuing an open command means the gate physically opened. Record command status and actual gate status separately where hardware feedback is available.
Every successful entry or exit must have a unique event identifier.
Prevent duplicate records caused by repeated sensor readings or network retries.
Entry and exit directions must be identified correctly.
Manual operations must be distinguishable from automatic RFID/fingerprint operations.
Failed authentication attempts must not be counted as successful entries or exits.
The application must handle temporary ESP32-to-Raspberry Pi communication failures.
The system should not rely on internet-based authentication or external APIs.

Understand the implemented RBAC and authentication system.
Identify existing ESP32 communication mechanisms, if implemented.
Reuse existing components, utilities, conventions, and architecture wherever possible.

Do not unnecessarily rewrite existing working functionality.

When implementing new features:

Follow the existing coding conventions.
Use clean, modular, maintainable code.
Keep hardware communication logic separate from business logic.
Validate all incoming device requests.
Implement appropriate error handling and logging.
Maintain database consistency.
Respect existing RBAC permissions.
Avoid introducing unnecessary dependencies.
Do not assume that hardware functionality exists unless it is confirmed in the codebase.

If any required functionality is missing, first explain what is missing and propose the appropriate implementation.

When modifying code, provide complete, working implementations rather than incomplete pseudocode.

8. Primary Project Objective

The ultimate goal is to develop a reliable, secure, and fully offline-capable Smart Gate Management System in which:

Employees can enter and exit using their registered fingerprints or RFID cards.
Gates open automatically after successful authentication.
Security guards can manually control gates through a secure web interface.
All entry and exit activities are automatically recorded.
Administrators can monitor employee movement and gate activities in real time.
All application data is maintained locally on the Raspberry Pi.
The complete ecosystem operates over the organization's LAN without requiring internet access.

Important development principle: Build on the existing project rather than starting from scratch. Preserve the already implemented RBAC and login system, and integrate all new features into the existing architecture.
